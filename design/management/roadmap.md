# 路线图与工作队列

这是轻量规划板，不代表事项已经实现。每次开始一项工作前确认当前代码和验收标准；完成后更新状态及开发上下文。

## P0 · 建立可验证的开发基线

- [ ] **试玩基线**：按 `development-workflow.md` 跑通并记录当前完整胜负流程、英雄选择、暂停和双语切换。交付：可重复的回归清单及现存问题。
- [ ] **素材目录审计**：盘点角色/图标的真源、生成产物、游戏引用、尺寸与锚点。交付：缺失/重复清单，不直接批量重生成素材。
- [ ] **平衡观察模板**：记录英雄、构筑、阶段、单局结果和异常强度。交付：首轮试玩记录与需要验证的假设。

## P1 · 核心游戏体验

- [ ] **波次与区域节奏**：逐区域验证敌人数量、间隔、难度上升及休整时长。依赖：试玩基线。交付：明确的节奏目标和可验证的波次调整。
- [ ] **成长选择可读性**：评估升级、装备、营地选择的候选质量、说明和相互作用。依赖：平衡观察。交付：能让新玩家看懂的选择反馈和规则。
- [ ] **英雄差异化**：对每名英雄记录定位、强势场景、技能与天赋协同。交付：每个角色可辨识的打法及回归案例。
- [ ] **战斗可读性**：检查敌人预警、伤害反馈、危险范围和 HUD 信息层级。交付：关键战斗状态有一致、及时的视觉反馈。

## P2 · 内容与可维护性

- [ ] **内容数据边界**：审查敌人、关卡、装备和天赋数据的重复配置，确定是否需要统一数据校验。依赖：P1 规则稳定。
- [ ] **素材规范**：约定新角色/动画帧的尺寸、锚点、命名、来源和授权记录。交付：新增素材不需要猜目录或引用方式。
- [ ] **回归自动化评估**：在确定稳定的核心验收流程后，评估是否引入浏览器自动化；此前不为自动化而引入不必要的工具或依赖。

## P3 · 体验与发布准备

- [ ] **浏览器/屏幕支持矩阵**：定义最低支持目标，验证窄窗口、高分辨率和输入设备。
- [ ] **无障碍与易用性**：评估键盘导航、对比度、文本缩放及非颜色提示。
- [ ] **发布检查**：确定版本记录、变更摘要、素材授权复核和部署后的 smoke test。

## 优先级规则

先解决阻断完整游戏循环、数据丢失或高频误操作的问题；随后改善战斗易读性和构筑选择；最后扩内容、视觉润色或基础设施。每次最多推进少量工作项，并把未验证的假设标为“待验证”，不要用确定语气描述。
