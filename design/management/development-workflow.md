# 开发流程与质量门槛

适用于个人或小团队开发。每项变更从可验证的玩家目标开始，以可运行的游戏验证结束。没有测试框架时，手工检查清单就是当前交付门槛；不要把“脚本语法通过”当成玩法正确。

## 从想法到交付

1. **描述问题**：记录玩家遇到的问题或机会、目标玩家、预期结果和不做的内容。
2. **缩小范围**：将工作拆成一项可以单独验证的小改动；写清验收条件、影响系统、素材和依赖。未知规则先做低成本原型。
3. **先设计再实现**：更新 `game-design.md` 或明确具体规格；玩法改动至少定义输入、状态变化、反馈、失败/边界情况。
4. **定位代码与素材**：查阅 `../../dev-context.md`，按数据、规则、呈现和 UI 的职责选择模块。确认素材的真源、运行时引用和生成命令，避免编辑生成后会被覆盖的产物。
5. **实现最小完整切片**：让规则、画面、提示文案、双语文本和必要素材一起闭环；变更共享流程前先列出受影响系统。
6. **验证与试玩**：运行下列静态检查，打开真实游戏验证验收条件及相邻流程；记录浏览器、英雄、区域和可复现步骤。
7. **审查与交付**：复查差异、路径、素材大小、错误控制台消息及语言覆盖；更新上下文/设计文档，按主题提交，并记录已知问题与后续待办。

## 验收门槛

- **所有改动**：仓库状态和差异仅包含预期文件；浏览器控制台无新增错误；相关页面可重新载入。
- **JavaScript**：对修改的脚本运行 `node --check js/<文件名>.js`。
- **角色素材**：用管理台预览并确认帧、透明背景和像素边缘；检查 manifest 的宽高与锚点；若编辑了精灵定义，再执行 `node scripts/build-character-assets.mjs`。此命令会覆盖导出的角色 SVG。
- **图标素材**：修改 `assets/game-icons.svg` 后运行 `node scripts/build-icons.mjs`（现有脚本调用 Windows PowerShell），确认图标选择页和游戏 bundle 均显示新图标。
- **玩法/UI**：至少验证主菜单、英雄选择、开局与 HUD、移动/攻击、技能、升级、拾取或装备、暂停、阵亡/胜利结算中与改动有关的路径。
- **双语内容**：用游戏语言按钮逐项切换英语和简体中文；检查布局溢出、tooltip、卡片和状态提示。
- **风险改动**：涉及伤害、存档、阶段推进、全局输入或生成器时，增加对应边界检查与回归试玩记录。

当前仓库没有配置自动化测试、lint、构建流程或 CI；不要声称这些检查已通过。涉及脚本生成时，在运行前确认源文件并准备好 Git 差异/备份，确认导出结果没有覆盖手工修改。

## 变更记录建议

每个工作项保留以下信息：目标与验收标准、受影响文件/系统、实际验证步骤和结果、素材来源与授权（如适用）、风险/回滚方法、后续待办。若设计决定改变，记录决定和原因，而不只留下最终数值。
