# 游戏设计基线

## 产品目标

Pixel League 是一款浏览器运行、可快速开始的单人等距视角动作 Roguelike。玩家操纵英雄，在五个区域中清理敌潮、成长和收集装备，最终击败区域首领。目标是让每一局都形成清晰的“战斗—选择—构筑—挑战”节奏。

## 核心体验原则

1. **易读的战斗**：敌人、攻击预警、危险区域、玩家生命与技能冷却要有明显视觉区别。
2. **有意义的成长**：升级天赋与掉落装备应让构筑发生可感知变化，而不是只堆叠难以比较的数值。
3. **英雄有辨识度**：英雄的基础属性、技能和专属天赋形成不同打法，资源规模允许时再扩展英雄数。
4. **低摩擦游玩**：无需安装依赖或账号即可在浏览器开始；输入、暂停和结算反馈保持一致。
5. **范围可控**：先验证单个完整游戏循环与稳定性，再扩内容和做跨平台/多人服务。

## 当前游戏循环

```text
标题 / 英雄选择
  → 开始单局 / 进入区域
  → 休整 → 敌人波次 → 区域首领
  → 战利品与升级选择
  → 传送门 / 营地商店 / 下一阶段
  → 最终胜利或阵亡结算
```

项目现有实现包括五个区域、18 级上限、升级天赋、英雄技能、装备掉落、营地与局外成长。调整循环时检查 `js/spawner.js`、`js/ui.js`、`js/combat.js`、`js/data_enemies.js` 和 `js/data_talents.js`，并同步更新 `dev-context.md`。

## 内容与系统约束

- 每个可游玩英雄应有明确的战斗定位、被动、Q/W/E/R 技能和升级路线；文案需支持英文与简体中文。
- 每项新增装备或天赋须说明触发条件、数值变化、叠加方式和玩家可见反馈；被动规则集中于现有战斗/属性入口。
- 新敌人进入关卡敌人池之前，应具备可辨识的行为、威胁提示、掉落规则和对应素材。
- 新素材需登记来源、用途、尺寸/锚点、授权与游戏内引用位置；同一素材避免保留多个未标明真源的副本。
- 游戏平衡采用可复现的记录：注明英雄、关卡、构筑、测试观察和变更原因，不以单次随机对局推断强度。

## 待确认设计决策

以下内容应通过试玩记录或小型原型验证后再定案，而不是当作已存在的功能：

- 单局时长目标，以及每波/每区域的节奏指标。
- 五区域的难度曲线、奖励差异和最终首领机制。
- 升级卡与装备词条的候选数量、稀有度、选择频率和局内上限。
- 局外成长对局内强度的影响程度，以及是否需要可重置的难度/进度。
- 目标屏幕尺寸、最低浏览器版本和移动端是否属于正式支持范围。
